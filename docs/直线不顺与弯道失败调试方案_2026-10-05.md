# 小车直线不顺与弯道失败：分层调试与里程计标定方案

日期：2026-10-05。依据本桌面工程的 ROS1 和 STM32 源码制定。

后续状态更新：本轮地面标定已完成记录，新默认有效轮径为 0.166224818 m、有效轮距为 0.408879504 m、计数为 4096，见 [里程计校准结果_2026-10-05.md](里程计校准结果_2026-10-05.md)。下文保留原始诊断方案和当时的参数快照；按用户要求，目前暂不继续建图或导航调试。

结论：你已补充“到弯道前停止”。先定位这一停车发生在哪一层，再按“反馈语义与方向 → 底盘低速响应 → 里程计标定 → 控制换算 → 雷达/定位 → 弯道几何 → 导航参数”检查。里程计误差值得检查，但目前不能确认它是唯一根因。

本次仅查看源码并编写方案；未连接实车采样、发送运动指令、烧录固件或改变运行参数。磁盘上的固件是否就是实车已烧录版本、现场使用哪个启动入口，均待确认。下面的命令供现场人员按步骤执行。

## 0. 针对“弯道前停止”的优先诊断

先按第 2 节设置环境并录制失败过程。第一次复现先保留现场原配置，从进入弯前到停住后继续记录约 10 秒，人工观察前墙距离与车身位置，不先调整轮径/轮距。

在多个终端同时观察，或录 bag 后对齐同一时段：

```bash
r1 rostopic echo /cmd_vel
r1 rostopic echo /stm32_command_sent
r1 rostopic echo /control_source
r1 rostopic echo /front_obstacle_distance
```

同时看 `/safety_stop`、`/safety_collision_prediction`、`/odom` 和导航终端日志。前方减速 `front_slow` 本身不会把 `/safety_stop` 置 true，因此不能只盯着这个布尔值。

| 停车瞬间的数据 | 停车层级 | 立即下一步 |
| --- | --- | --- |
| cmd_vel 的 v/w 都为零；sent 也为零 | 导航没有给出运动，或目标/指令来源有问题 | 看全局/局部路径、TEB infeasible/控制周期/目标状态，核对实际使用的插件 |
| cmd_vel 非零；sent 归零；source 含安全停车原因 | 串口桥保护截断 | 按具体原因检查距离、雷达新鲜度、车体扫掠与外参 |
| cmd_vel 的 v 非零；sent 很小；source 含 front_slow；轮子停住 | 减速命令可能落入驱动器低速死区 | 在开阔区测最低稳定轮速，核对实际下发与轮速响应 |
| sent 的 w 非零；实车不转；编码器也不增 | 电机执行/死区/机械阻力 | 看驱动器状态、轮速单位、模式和低速左右转试验 |
| sent 的 w 非零；编码器显示转动；车身不转或转得明显不符 | 滑移或里程计/字段语义问题 | 用外部角度测量分清真实转动与计数估计 |

代码中的前方减速比例为：

```text
scale = (front_clearance - 0.15) / (0.60 - 0.15)
v_sent = v_request × scale
```

例如前方车头余量 0.30 m，比例为 1/3；请求 0.15 m/s 时，下发仅 0.05 m/s。如果驱动器此时不能稳定起步，会出现“离弯还有距离就不走了”。若余量到 0.15 m，则直接禁止前进。公式中的距离从车头边缘起算，不是雷达到墙距离。

另一个待验证的冲突：TEB 当前 `min_obstacle_dist=0.03 m`，串口桥前进停车余量为 0.15 m。局部轨迹可能计划再靠近前墙后转向，而安全层提前禁止继续靠近。两者不是同一种约束，不能仅凭数值不同就下结论，但这是弯前停车的重要检查点。

此时保留保护，验证当前位置是否有安全原地转向空间、规划是否请求了转向、人工前进轨迹能否更早完成转弯。若空间本就不足，应调整转向位置/全局路线或几何方案，不能直接把停车距离降到 0.03 m。减速过程只缩小 v、保留 w 时也会改变曲率，应对比规划轨迹与经过安全处理后的轨迹。

这个顺序可以在一次有效录制后把问题缩小到导航输出、安全截断或底盘执行，再决定是否需要深入标定。

## 1. 当前工程中已确认的关键事实

| 环节 | 源码/配置中的现状 | 对调试的意义 |
| --- | --- | --- |
| 里程计尺度 | `wheel_diameter=0.20894 m`，`wheel_base=0.51375 m`，`ticks_per_rev=4096` | 注释写“实车标定”，仍需新的原始记录验证 |
| 反馈左右通道 | `/wheel_encoder.data[1]` 当物理左轮，`data[0]` 当物理右轮 | `/stm32_feedback_text` 的 left/right 是协议通道名，不能直接认作物理左右 |
| 编码器方向 | 左右默认 sign 都为 `+1` | 必须用前进、单轮和左右转试验确认 |
| 计数处理 | 16 位有符号累计计数差分；已有回绕处理和首帧建立基准 | 不宜重复添加未经验证的回绕“修复” |
| 里程计时刻 | 编码器消息是无 Header 的 `Int16MultiArray`；`dt` 用 ROS 回调收到数据的时间 | 串口积压可能污染瞬时速度，不能仅看累计位置 |
| MCU 控制换算 | `Core/Src/main.c` 中 `L=407.0f`，单位 mm | 控制轮距 `0.407 m` 与里程计有效轮距 `0.51375 m` 不同，优先实测 |
| MCU 反馈 | 大约每 50 ms 上报一次当前编码器变量 | 理论上约 20 Hz；上报存在不等于 CAN 数据新鲜 |
| 串口桥 | 100 Hz 主循环；发布 `/stm32_command_sent`、`/control_source` 和安全状态 | 可区分导航输出与经过安全处理的命令；sent 不是驱动器确认已执行 |
| 默认建图入口 | `build_map.sh` 启动 `slam_toolbox_build_map.launch` | 另有 Gmapping 入口，排障时避免两套同时运行 |
| 默认导航入口 | `navigation_stack.launch` 使用 TEB，控制频率 12 Hz | 修改 DWA YAML 对这个入口无效，现场应读取实际参数 |
| 车体 | 以轮轴中心地面投影为原点：前端 `0.3483 m`，后端 `-0.1517 m`，半宽 `0.24 m` | 非对称车头转弯扫掠明显；不能只按宽度判断能否过弯 |
| 雷达外参 | `x=0.315 m`，`y=0`，`z=0.33 m`，`yaw=0` | 手工测量误差也可能来自雷达安装角和车体原点 |
| 雷达安全层 | 前方余量 `0.15 m` 停车，`0.60 m` 起减速，扫描超时 `0.30 s` 停车 | 前方墙面可能导致“走走停停”；关闭保护会掩盖原因 |
| 默认自主倒车 | 禁止 | 如果某弯必须前后调整才能通过，当前策略可能无解 |

特别注意两点：

1. ROS 里程计的有效轮距不等于尺量轮中心距。滑移转向时，它还包含地面、载荷、轮胎变形等影响。代码注释中的物理轮距 `0.425 m` 也不是本次重新测量结果。
2. `serial_bridge` 的 `max_v/max_w` 当前主要用于手柄轴映射，并未在 `/cmd_vel` 分支按这两个值进行限幅。自动导航降速应修改实际使用的 TEB/DWA 速度限制，不能只传 `max_v:=0.15` 就认为自主速度已被限制。

## 3. 第一关：反馈字段、左右轮和符号

先架空或按底盘允许的方式单轮检查。若减速器不能反拖，不强行用手转轮，改由现场操作员作短时低速单轮试验。关闭其他会发速度的节点，保留安全处理。

```bash
r1 rostopic echo /wheel_encoder
r1 rostopic echo /control_source
r1 rostopic echo /stm32_command_sent
```

依次检查并记录：

1. 静止 30～60 秒：两路计数应基本不变。振动、抖动和机械回弹另行记录。
2. 只让物理左轮沿前进方向转动：按现有代码应主要改变 `data[1]`。
3. 只让物理右轮沿前进方向转动：应主要改变 `data[0]`。
4. 两轮一起前进：经过现有符号转换后两路累计增量都应为正；`/odom.twist.twist.linear.x` 应为正。
5. 实车左转：ROS 的正 `angular.z` 应对应左转，原始里程计 yaw 也应增加。右转则相反。
6. 轮胎作标记，每个物理轮精确转 5～10 圈，逐帧累加计数增量，求“轮胎一圈的反馈计数”。左右各做三次，核实是否真为 4096。

编码器可能在电机轴，也可能经驱动器换算到轮轴；同时核对减速比和计数倍频。源码仅取出驱动器反馈字节，不能据此证明它必然是累计编码器位置。字段必须在匀速转动时继续累计、停车后保留位置；若它匀速时近似常数、停车归零，则可能是速度字段，须先对照驱动器协议解决。

当前反馈为有符号 16 位，单步增量计算：

```text
delta = ((current - previous + 32768) mod 65536) - 32768
```

长距离/多圈必须逐帧求差再求和，不直接用最终值减初始值；每两个有效样本间真实增量必须小于半个计数范围，否则无法唯一判定圈数。

只有确认通道错误才更改左右映射；只有确认方向错误才更改 encoder_sign；角速度电气符号参数与编码器符号应分别验证。不要在 ROS、串口和 MCU 多处同时“反一下”。

## 4. 第二关：反馈时序与底盘低速响应

频率与时间检查，各运行约 30 秒后 Ctrl+C：

```bash
r1 rostopic hz /wheel_encoder
r1 rostopic hz /odom
r1 rostopic hz /scan_raw
r1 rostopic hz /scan
r1 rostopic delay /scan
r1 rosrun tf tf_monitor odom base_footprint
```

编码器上报/odom 应接近 MCU 的约 20 Hz，具体以测量为准。雷达 launch 的 `scanfreq=30` 不能证明实机是 30 Hz，因为 `configure_sensor=false`，当前不会在启动时重新写入该设置。检查实际帧间隔、重复 stamp、最大间隔、队列积压和 TF 外推警告；单看平均 Hz 不足以验收。

当前 `/wheel_encoder` 无采样时间；MCU 即使没有新的 CAN 心跳，也能每 50 ms 重发旧变量。因此“有 20 Hz 消息”不等于“有 20 Hz 新编码器”。需要结合计数是否长时间冻结、CAN 心跳接收时刻和驱动器状态检查。

画速度对比图，若容器已有 rqt_plot：

```bash
r1 rosrun rqt_plot rqt_plot \
  /cmd_vel/linear/x /stm32_command_sent/linear/x /odom/twist/twist/linear/x \
  /cmd_vel/angular/z /stm32_command_sent/angular/z /odom/twist/twist/angular/z
```

手柄直控时 `/cmd_vel` 可能不是当前有效命令，以 `/control_source` 和 sent 为准。用外部测量检验实际运动，避免拿未标定 odom 当速度真值。

在足够空旷、平整的比赛地面，先用手柄或独立的限时测试控制器做低速试验，不带导航闭环：

- 前进目标参考 `0.05、0.10、0.15、0.20 m/s`，从短时间开始，逐项检查能否稳定起步，先后各做三次。
- 原地左右转参考 `0.20、0.35、0.50 rad/s`，按空间缩短时间；这组参考不是强制最低速度。
- 用 0.5～1 秒平缓加速和减速，与突变命令对照；记录开始运动延迟、实际速度、稳态波动、停车延迟和重复性。
- 使用实体地面标记或俯视视频测距离和转角。额外记录零速命令后的真实停车过程。

原因分流：

| 观察结果 | 优先检查 |
| --- | --- |
| sent 稳定，实车仍一顿一顿 | 驱动器低速死区、速度环、供电、摩擦、轮胎/支撑轮卡滞 |
| sent 稳定，物理运动平滑，但 odom 速度交替为零和尖峰 | 反馈心跳重复、串口批量到达、回调 dt；先检查时间链路 |
| 编码器连续但实际原地打滑 | 地面/轮胎/载荷，不能仅靠调整轮距解决 |
| sent 明显小于请求，source 带 `front_slow` | 安全层正在主动减速，观察真实车头到墙距离 |
| sent 为零，source 带 `lidar_timeout_stop` | 雷达消息新鲜度、网络丢包或进程阻塞 |
| sent 的 v 为零但 w 保留，source 带 `trajectory_stop_turn_allowed` | 平移轨迹被拦截，但当前位置允许转向 |
| sent 的 v/w 都为零且带 `trajectory_collision_stop` | 当前预测的完整车体扫掠碰撞，先检查几何和雷达外参 |
| source 是 joystick/goal_stop_latched/idle | 指令抢占、终点锁止或命令过期，并非尺度误差 |

源码中的 CAN 驱动层直接转发左右轮速，本工程未见在这条链路中实现轮速 PID。若需调 PID，先确认速度闭环位于哪一个电机驱动器及其可调参数，不能凭空在 ROS 上添加位置补偿来替代速度环。

对 dt/新鲜度问题的后续最小修复候选：带真实采样时刻/序号的反馈、CAN 反馈超时状态、合理的速度估计窗口。它们可能涉及协议协调，需先留下日志证据；不要只把速度曲线滤平，也不要把陈旧反馈标成新采样。

## 5. 第三关：直线尺度标定

### 5.1 测量方法

先完成计数/圈数核实。选择比赛地面，使用轮轴中心地面投影作为车体位置基准，固定载荷。

1. 地面画长 2～3 m 的直线，有空间可增加到 5 m；标出起终点。
2. 车体起始航向对齐，记录两轮初始计数和 odom 位姿。
3. 使用稳定低速走直线，人工按真实终点停下，等车完全停稳后取终值。不要根据 odom 自动停车来定义真值。
4. 测真实轴心位移、末端横向偏移、真实航向变化；若轨迹明显弯曲，此组不能直接用两端直线距离作路程标定，应先解决直行问题或使用视频重建真实路径长。
5. 做至少五组；再以另一速度和相反行驶方向复验。当前自主倒车受限，相反方向可调转车头后继续向前，不需要解除自主倒车限制。

必须用原始 `/odom` 或编码器，不能用 AMCL/map 位姿做轮式里程计标定真值。SLAM 会纠偏，容易掩盖误差。

### 5.2 修正公式

近似直线且航向基本不变时：

```text
k = π × wheel_diameter / ticks_per_rev
S_odom = k × (累计左轮增量 + 累计右轮增量) / 2
wheel_diameter_new = wheel_diameter_old × S_true / S_odom
```

例：真实走 3.00 m，原始里程计走 3.15 m：

```text
D_new = 0.20894 × 3.00 / 3.15 ≈ 0.19899 m
```

这是示例，不是给本车的最终数值。已知每轮一圈计数时，应优先直接求米/计数 `k`；若 ticks 尚不确定，仅靠直线试验只能识别 `D/ticks` 的比例，不能同时确定两个参数。

多组可做过原点的最小二乘拟合：设 `N_i=(ΔN_left+ΔN_right)/2`，则 `k_new=Σ(N_i×S_true_i)/Σ(N_i²)`；检查残差是否随速度、电量或距离变化，不只取一组结果。

注意区分两种偏航：

- 实车直行而 odom 弯曲：检查左右编码器尺度/映射；需要分别辨识 `k_left、k_right`。
- 实车本身弯曲而 odom 也正确显示弯曲：优先调左右实际速度一致性、摩擦和机械状态；只改里程计会让电脑误以为车已走直。

当前 `odom_publisher` 左右使用同一个 `tick_to_m`，不能单独校正左右轮尺度。如果外部直线基准显示必须分别补偿，再添加明确的左右尺度参数；同时评估控制端左右增益，保留参数为 1 时的行为。不要一开始就扩大修改范围。

## 6. 第四关：有效轮距与控制角速度分别标定

### 6.1 先标定里程计有效轮距

完成直线尺度后，在开放区域画角度参考线，以车体标记测真实 yaw。测试左右 `90°、180°、360°`，每个方向至少三次；再做比赛所需的低速圆弧。不要用“角速度指令×时间”代替真实角度。

当前代码把 yaw 归一化到 `[-π, π]`。做 360° 时最终 yaw 接近初始值，不能据此认为转角为零；应逐帧解包并累加：

```text
delta_yaw_i = atan2(sin(yaw_i - yaw_(i-1)), cos(yaw_i - yaw_(i-1)))
theta_odom_total = Σ delta_yaw_i

b_new = b_old × theta_odom_total / theta_true_total
```

正负符号必须一致，单位统一为 rad；方向反了先修符号，不用负轮距补偿。

例：真实左转 360°，原始 odom 累计只有 300°：

```text
b_new = 0.51375 × 300 / 360 = 0.428125 m
```

如果 odom 比真值大，应该增大 b；如果比真值小，应该减小 b。

直接从编码器计算更清楚：`b_new=(k_right×ΔN_right-k_left×ΔN_left)/theta_true`。直线尺度与有效轮距有耦合，必须按顺序标定，不能轮径/轮距同时凭感觉改。

如果左右转、不同速度、不同地面得到的 b 差别显著（例如超过约 5%），先重复测量排除人为误差，再检查滑移、机械阻力和模型适用范围。稳定的常数误差可以标定；随机滑移需机械改善或融合独立传感器，不能用一个 b 消除所有情况。

### 6.2 再验证 MCU 控制换算

当前 MCU 将角速度转轮速：

```text
v_left_mm_s  = v_mm_s - w_mrad_s × 407 / 2 / 1000
v_right_mm_s = v_mm_s + w_mrad_s × 407 / 2 / 1000
```

在驱动器轮速单位准确、执行无额外增益和滑移模型稳定的条件下：

```text
|w_odom| ≈ |w_sent| × 0.407 / 0.51375 ≈ 0.7922 × |w_sent|
```

例如请求 `0.60 rad/s`，理想反馈约 `0.475 rad/s`。这只是从磁盘代码推导的待验证假设，不能当作已测得结果。驱动器自身的轮径/减速比设置也可能引入另一尺度误差。

里程计标定正确后，测试多个恒定 v/w 与左右方向，比较 sent、校准后的 odom 和外部真实速度。如果实际角速度存在稳定比例误差，再在确定驱动器单位和已烧录版本后修正 MCU 控制换算，或在明确的一处做控制补偿。验证工作应包括新固件编译、烧录校验、架空方向检查及落地实测。

不要直接把 TEB 的 `wheelbase: 0.0` 改成有效差速轮距。TEB 这个参数用于车式转向命令的轮轴距离，当前差速模式 `cmd_angle_instead_rotvel=false`，含义不同。[TEB 官方参数定义](https://github.com/rst-tu-dortmund/teb_local_planner/blob/noetic-devel/cfg/TebLocalPlannerReconfigure.cfg)

## 7. 第五关：雷达安装、TF、地图和定位

车体坐标约定：x 前、y 左、z 上；轮轴中心地面投影是当前 `base_footprint` 原点。确认车头前后尺寸、雷达位置、轮距的测量都用同一参考。

```text
map → odom → base_footprint → laser
```

`odom` 应连续，允许逐渐漂移；地图定位可通过 `map→odom` 纠正全局漂移。当前轮式里程计发布 `odom→base_footprint`，SLAM 或 AMCL 发布 `map→odom`，每条边应只有一个发布者。[ROS REP 105](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst)

```bash
r1 rosrun tf tf_echo odom base_footprint
r1 rosrun tf tf_echo base_footprint laser
r1 rosrun tf tf_echo map odom
r1 rosparam get /use_sim_time
```

实机应使用真实时间，`use_sim_time` 为 false 或未设置。架空转轮时地图不是真实运动，不能用来评判 SLAM 几何效果。

按以下顺序验证：

1. 静止在直墙前，RViz Fixed Frame 设 `base_footprint`，核对墙的方向、前后/左右和车头到墙的距离。注意 `/front_obstacle_distance` 按车头边缘余量计算，并非从雷达中心起算。
2. 同时显示 `/scan_raw` 与 `/scan`，确认滤掉的是车体回波，没有因错误外参/过大轮廓误删近墙；不能无限增加滤除范围来获得“干净地图”。
3. 在已核实雷达量程的区域以量尺检查点距。核对雷达 yaw、水平安装与支架牢固程度。
4. RViz Fixed Frame 设 `odom`，观察低速直线与转动时墙面是否在固定环境坐标中保持稳定。小幅轮式漂移可存在；出现明显双墙/旋转墙应区分 odom、时间戳和扫描运动畸变。
5. 如果静止对齐而一转弯就撕裂，检查每帧 stamp 单调性、`scan_time/time_increment`、TF 的扫描时刻可用性和网络延迟。当前雷达驱动已存在更新时间戳的修复代码，先验证效果，不能认定问题已经消失。
6. 重新建图时低速经过直线、圆弧、左右拐角，利用有辨识度的场景作回环。标定前后的地图分别保存，检查真实通道宽度、墙间距、重复墙和回环对齐。
7. 导航在 RViz 设置正确初始位置；观察 AMCL 点云、`amcl_pose` 和激光与地图的吻合情况。低速短程后定位应继续合理，避免平行墙环境匹配到相邻通道。

如果原始 odom 平滑但 `map→odom` 持续大幅纠偏、激光在相邻墙之间跳动，则重点检查地图/定位，而不是继续改轮径。AMCL pose covariance 只能辅助判断，不能用“小协方差”证明定位一定正确。

标定或雷达外参有明显变化后建议重新建图验证。旧地图可以保留作对照，但不能默认它与新配置一致。

## 8. 第六关：弯道的几何可行性

目前车宽 0.48 m，costmap 每侧 padding 0.02 m。仅就直线截面而言，名义宽度已约 0.52 m，尚未包含定位误差、地图栅格和实际安全余量。宽度接近这个值的通道不适合用“缩小 footprint”强行通过。

车头伸出轮轴中心 0.3483 m。裸车体前角到轮轴中心距离：

```text
r_front = sqrt(0.3483² + 0.24²) ≈ 0.423 m
```

按安全预测的矩形每边扩 0.03 m 时，前角半径约 `0.465 m`。因此，包含整个扫掠圆的开放空间直径约 0.93 m，是保守的充分空间条件；不是所有 90°/180°弯道的必要通道宽度。是否能经过某个弯必须按具体位置和完整运动轨迹检查。

每个失败弯测量：进/出通道宽度、内外拐角位置、可用于转向的区域、车体转向时轮轴位置、实际障碍和地图障碍是否一致。分别验证：

- 在开阔区原地转是否正常？异常则先回到控制/机械层。
- 同一弯人工低速能否通过？若能，记录人工轨迹与转向位置，检查是否依赖倒车或明显轮胎打滑。
- 人工前进即可过弯，而自动失败：比较定位、全局路径、局部轨迹和安全截断。
- 人工必须倒车调整才能通过：当前禁止自主倒车可能确实没有可行解，需重新设计路径/转向策略与观察覆盖，不能直接解除限制。
- 全局路径过内角，但局部规划始终无解：Navfn 的全局路径不能作为完整非对称车体扫掠可行的证明，需要让路线/过弯位置给车头留空间。

保留真实车体轮廓及停车保护。先纠正外参/定位/轨迹，再考虑软代价参数；膨胀层的非致命代价不是一律不可走，不应简单按“车宽 + 两个 inflation_radius”计算通道能否通过。

## 9. 第七关：在底盘和定位通过后调导航

先读取实际插件。当前默认是 TEB，DWA 配置文件不会同时生效。

测试准备：车已停车、旧目标已取消、没有其他自主任务在持续给目标。保留原参数记录。对 TEB 可通过动态配置设置一组低速起点：

```bash
r1 rosrun dynamic_reconfigure dynparam set /move_base/TebLocalPlannerROS \
  '{max_vel_x: 0.15, max_vel_theta: 0.35, acc_lim_x: 0.20, acc_lim_theta: 0.60}'
r1 rosparam get /move_base/TebLocalPlannerROS
```

这些是初始试验上限，不是最终比赛配置。如果所用版本同时启用 `max_vel_trans`，也核对其限制；如果已经测出低速起步死区，实际试验点应在可稳定运动的范围内选择。TEB 速度和加速度参数的含义依据[官方配置定义](https://github.com/rst-tu-dortmund/teb_local_planner/blob/noetic-devel/cfg/TebLocalPlannerReconfigure.cfg)。

`rosparam set` 不保证动态节点立即重读参数；TEB 使用动态配置工具。当前 odom 几何参数则在节点启动时读取，标定修改后必须在停车并退出原 launch 后重启，保持整个系统参数一致。

按以下顺序，每项至少三次：

1. 开阔区 2～3 m 直线目标：目标姿态与直线一致，观察角速度是否反复变号、速度是否抖动，以及实际横向偏差。
2. 开阔区左右 90°：排除墙体限制，检验角速度跟随与最终航向。
3. 宽通道直角弯：观察何时减速、何时开始转向，记录 TEB 轨迹和 sent。
4. 实际窄直角/回头弯：先定位正确，再逐步接近；看失败发生在无全局路径、无局部可行轨迹，还是独立安全层截断。
5. 全程连续运行：确认累计漂移、热机、电量变化和负载下的计算周期。

每次只改变一组有明确证据的参数：

| 确認的现象 | 下一步 |
| --- | --- |
| TEB 请求本身频繁摆动，定位稳定 | 检查全局路径是否反复换边、via-point 约束、替代路径切换；可对 `enable_homotopy_class_planning` 作单项对照 |
| sent 平稳但实车摆动/滞后 | 回到底盘速度环、控制增益、死区与机械层 |
| 请求稳定但安全层反复截断 | 检查实时墙面距离与完整车体扫掠；统一规划器/安全层对可执行轨迹的认识 |
| TEB infeasible 与地图/雷达墙面重合 | 检查真实空间、转向位置和 footprint；不能把碰撞约束调成“可碰撞” |
| 控制循环持续超时 | 查看 CPU/节点耗时；在日志证据下减少候选类别/优化负载，不盲目提高频率 |
| 仅近目标不断调整 | 检查目标姿态、yaw tolerance、停止阈值和可达到的最小转速 |

如果现场实际使用 DWA，再检查 `min_vel_theta/min_vel_trans` 与真实死区、`sim_time`、采样数和速度跟随；不把“增加采样数”当作通用过弯修复。当前 TEB 已为差速模式，保留 `min_turning_radius=0` 和 `cmd_angle_instead_rotvel=false`，除非查明底盘模型本身不同。

| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 01 | 待填 | 待填 | 待填 | 待填 | 待填 | 待填 | 待填 | 待填 |

建议把以下数值作为第一轮工程目标，最终按比赛通道余量收紧；不是 ROS 标准或机械安全认证：

| 检查项 | 第一轮目标 |
| --- | --- |
| 反馈和方向 | 左右物理对应正确；前进与左右转符号正确；无丢帧导致的跳变 |
| 底盘跟随 | 稳定命令下没有持续起停/左右摆动，低速死区与响应延迟已测得 |
| 直线距离 | 3 m 尺度误差 ≤2%，重复误差没有明显随速度变化 |
| 直线航向 | 3 m 真横向偏差目标 ≤5 cm，真实航向变化目标 ≤2° |
| 角度 | 左右 90°误差目标 ≤3°，360°累计误差目标 ≤5°，能重复 |
| 数据新鲜度 | 无持续积压/重复 stamp/外推错误；无超过 0.30 s 的扫描中断；按实测周期检查编码器异常长空窗 |
| 地图/定位 | 无明显重复墙；通道尺寸在测量与栅格误差范围内；低速过弯后定位仍与真实位置一致 |
| 过弯 | 左右代表弯各连续三次成功，车体不接触障碍，失败时保护状态可解释 |

若真实 yaw 偏差 2°，3 m 直行就可能带来约 10 cm 横向偏差；距离比例校准正确不代表狭窄通道能通过。定位误差和左右轮一致性应共同验收。

回滚按修改范围进行，先停车、退出原启动进程：

1. 仅临时动态配置：用备份参数中的原值通过 dynparam 恢复；重启且未改 YAML 时也会回到 launch/YAML 的默认值。
2. 已修改 odom/导航源码或 YAML：恢复本次实际修改的文件；源码需要重新编译，停车后重新启动。不要把整个备份目录覆盖回去，以免抹掉无关的新改动。
3. 已修改固件：恢复已保存的明确版本，重新编译/烧录校验并做方向与停车复查。仅恢复磁盘 `.c` 文件不会恢复板上固件。
4. 新地图另名保存，旧地图保留；切回时同时确认 `map_file` 和对应参数版本。

最终应分别报告：源码/离线检查、板端通信、实车底盘响应、里程计标定、地图定位、实际过弯。任何离线测试通过或软件保护触发，都不能替代落地机械试验。

## 11. 推荐执行顺序

第一轮先完成：保存现场参数和弯前停车失败 bag → 按第 0 节确定停车层级 → 单轮方向及每圈计数 → 低速直控与反馈时序 → 3 m 直线标定 → 左右多角度有效轮距标定 → 验证控制 `0.407 m` 差异。

第二轮再完成：雷达外参/TF 验证 → 重建并另名保存地图 → 初始化定位 → 开阔区导航 → 宽弯 → 比赛窄弯 → 单项导航参数对照与连续验收。

最有价值的第一份数据是：同一时段的 cmd_vel、sent、原始编码器、odom、scan、control_source，加上真实距离/角度。它能决定下一步应改哪一层，避免在错误层反复调参数。
